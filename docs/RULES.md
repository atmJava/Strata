# 工作章程（RULES）· v3 · 2026-10-25

这份文件定义"怎么干活"。结论与数字在 [`EVIDENCE_LEDGER.md`](EVIDENCE_LEDGER.md)，状态与决策在
[`HANDOVER.md`](HANDOVER.md)，工装规范在 [`../tools/server/README.md`](../tools/server/README.md)。
**章程本身可以改，但要在文末写版本行**（日期 + 改了什么 + 为什么）。

## 1. 决策权

- **执行自主，收口不自主。** 单项/单轮怎么做由我自己决定，不向用户提问；遇取舍选**最安全、质量最好、
  最推荐**的那条，不确定就选**可回滚**的那条。**目标级完成只能由用户确认**（见
  [`PORTING_RULES.md`](PORTING_RULES.md) §9），不得自行 complete。
- 只有三条硬约束不可越过：**上游只读**（不回帖、不开 PR、不提交任何东西）；**绝不提交没做过的测量**；
  **停机纪律**（见 §7）。
- 决策记录：生产改动进 HANDOVER §3 的决策表（含回滚），测量进台账（含判决）。

## 2. 每轮固定五步（不许跳）

1. **事前审查**：这件事做过没有（先查台账索引、上游、引擎自带的开关/工具）；能不能**免停机**；
   影响面（谁在用、回滚成本、要几次重启）；需不需要**源码核实**。
2. **计划**：写清假设、臂、判据、回滚命令；**先想清楚"如果结果为 0 怎么办"**。
3. **执行**：按 §3/§4 的规范；一次只改一个变量。
4. **验证**：原始日志 + 数字 + 是否逐字节恢复；没有证据就不算完成。
5. **归档与更新目标**：台账一条、HANDOVER 相应小节、服务器文档（运维相关时）；然后更新"下一轮做什么"。

## 3. 写代码之前（源码核实，不重复造轮子）

- **先核实源码**：要改的那段现在的实现、调用点、线程/流、生命周期；引用时写清文件:行。
- **先找现成的**：上游是否已有同类实现、env 开关、参数或工具（`--gpu-stages`、`STRATA_*_TIMING`、
  `--stage-timing`、`-DSTRATA_*` 构建选项）。**有就不写新的**，能复用就复用。
- **风格跟上游一致**：命名、注释口气（英文、说清为什么）、文件位置、头文件依赖、错误用 `std::string& err` 上报、
  不引入新依赖、不格式化无关代码。
- **默认路径逐位不变**，新行为一律放在**默认关的 env/flag**后面；构建选项改动另开构建目录，不动 `build/`。

## 4. 写代码时（资源、异常、探针、日志）

- **资源与竞争**：VRAM/RAM/线程/stream 各占多少、谁在并发读写、有没有锁或门铃（doorbell）、
  失败时所有资源都要能释放（RAII、`cudaEventDestroy`/`cudaStreamDestroy`/`free` 都写在析构里）。
- **异常与错误**：CUDA 调用逐个检查（`ck(...)`）；不吞错；早退路径要先把在飞的 DMA/stream 同步掉。
- **探针**：要能量出来（计数、`STRATA_*_TIMING` 相、`--dump-*`），**默认关**，开销可测（照 L-030 先量工装自己的代价）。
- **日志**：一行说清一件事，带数字与单位；不刷屏；默认路径不多打。
- **测试与门**：改数值要过逐位门（`parity_window.py`）或质量门（`quality_eval.py`／`agent_budget_ab.py`）；
  改性能要同 boot A-B-A、每臂 ≥3、报中位与离散度。

## 5. 证据规则

- **只写事实，不写推断**。读代码得到的结论标 **静态阅读，未测**。
- **<3% 不算结论**；跨 boot 比"小读/首字"这类小量按 **~7%** 看（L-031 实测）。
- 每个数字都要能追到**原始日志路径 + 脚本名**；写清"没测什么"。
- 仪器自己也有代价：先量仪器（L-030 的 +2.5–8%），再信读数。

## 6. 记录与去噪

- **一处一事**：结论进台账、状态/决策进 HANDOVER、运维/参数进服务器文档、工装用法进 `tools/server/README.md`；
  不在两处各写一半。
- 台账条目模板：一句话结论（带日期与臂数）→ 做法与臂 → 数字（中位/离散度）→ 判决 → **没测什么** → 日志路径。
- **不贴大段日志**，只给路径；不重复已有结论（引用编号即可）。
- 回复要短、密、可核；上下文只取需要的段落，不把历史倒一遍。
- 服务器上的文档与仓库同步：改完 `scp` + `ops-check-tool-sync.sh`（脚本）或人工比对（文档）。

## 7. 停机与安全

- 停机（>2 min）决定权在我：低峰跑、`cp -p` 快照、装完 `verify-running-config.sh` 核、
  测完**逐字节恢复**并 `cmp -s`、台账写清停了多久、今天第几次重启。
- 凭据不进仓库、不进文档；sudo 口令只留在服务器上被权限保护的两个脚本里。
- **`pgrep -f` 会匹配到自己的命令行**：脚本里等另一个脚本时用 `pgrep -f "[e]xp-env-ab.sh"`（或按 PID），
  否则那个 `while pgrep ...; do sleep; done` 会永远等自己（2026-10-24 踩了两次）。
- **一次只跑一个安装**：`use-config.sh` 还在等加载时不要再起第二个（两个安装器会互相覆盖配置；
  2026-10-24 就撞过一次）。动手前先看 `/health` 与 `pgrep -f use-config`，结束后必须核对配置内容而不是只看脚本返回。
- 删任何东西前：`readlink -f` 核对绝对路径、检查引用（unit / bin / config / 文档）、先备份再删。

## 8. 复盘与目标更新

- 每轮结束必答四问：**cron/timer 还在跑吗、有没有残留进程、`vram-perf.csv` 有漂移吗、方向要不要调**。
- 目标写在 HANDOVER（一页）；每轮把"下一轮先做"改成最新的一条，旧的结论进台账。
- 卡住时先降级成"能给出事实的最小实验"，不要重复同一个坑。

## 9. 编码与部署场景（改引擎代码时额外守的六条）

这一节是 2026-10-24 一场通宵里用代价换来的，专管"改代码 + 把它跑起来"这一段。

- **1. 部署验文件，不验产物。** 构建完先 `md5sum` 构建产物，**再 `md5sum` / `strings | grep <新字符串>` 部署路径**；
  两者一致才能启动。今天两次白跑都是"构建成功 ≠ 跑的是新二进制"。
- **2. 覆盖运行中的二进制只能 `cp … .new && mv -f`。** 直接 `cp` 会 `Text file busy` 并且**静默失败**
  （`cp` 的失败信息在后台任务里很容易被 `&&` 链吞掉）。
- **3. 后台构建不算完成**，直到它的 `exit code` 与产物时间戳都看过。不要在后台命令里串 `cp`。
- **4. 一个安装器**：动手重启前 `pgrep -af "[u]se-config|[r]estore-prod|[f]lag-ab|[e]xp-env-ab"` 必须为空；
  两次安装重叠会让 A 臂的热身撞上重启，整轮作废（今天发生过）。
- **5. 开关优先做成运行时 flag 文件**（`include/strata/core/runtime_flag.hpp`），不要再用函数内 `static` 读 env：
  env 开关 = 每臂一次冷装载（~190 s），flag 文件 = 同 boot 交替，跨 boot 漂移（今天实测到 9%）不再是天花板。
  默认路径逐位不变：没有文件时行为与 `getenv()` 完全一致。
- **6. 每轮先写判据再动手，收尾必须留证据**：哪个日志、哪条命令、哪个脚本、以及"没测什么"。
  没有证据的那一轮按未发生处理，不进台账。
