## L-001 · GPU0 显存预留 960 → 1280（待执行）

它**不保证**之后仍有这么多空闲；本 boot 之后又被吃掉 455 MiB。所以把 GPU0 预留从 960 提到 1280，
预期 plateau 从 ~505 抬到 ~825 MiB，脱离 512 的告警线；代价是 GPU0 专家缓存少 320 MiB（约 135 slot，−1.8%）。

**为什么不是 1024**（引擎自己建议的数）：1024 只补 64 MiB，plateau 约 569 MiB，距告警线只有 57 MiB；

**判据**（这是稳定性改动，不用速度判胜负）：
1. 重启后同一负载下 `WARNING: only N MiB ... (#2065)` 不再出现（或 N 稳定 > 700 MiB）；

## L-002 · 思考 token 预算（下一个候选，未开始）

**观察**（同一批探针，只读）：`max_tokens 400` 时思考吃掉 218 token、答案 0 个 ——
日志原话 `the reply reached max tokens while still thinking, so it has no answer`；
`max_tokens 500` 时思考 268、答案 350。配置里 `reasoning_budget_tokens = 12288`，
等于**思考基本不设上限**，只在撞到 `max_tokens` 时才收。

**为什么值得做**：这是 L1（任务墙钟）上唯一不需要重编译、不需要重启引擎就能试的杠杆——
调优记录 §21.2 自己估过"思考 −64% ≈ 墙钟 −25%"，比任何 kernel 改动都大。

**风险**：思考变短可能让工具调用正确率下降（`tool_call_recovery`、`reasoning_loop_recovery=recover` 是兜底，不是质量保证）。
**所以判据必须是任务级**：同一批 agent 任务，报完成率、工具调用通过率、空答案率、墙钟中位，不能只看 tok/s。

**已查清（2026-10-24，读源码 + 实测）**：

- `reasoning_budget_tokens` 是**请求级**参数：`serve/server.py:4100-4109` 的 `reasoning_budget()` 先取请求自己的值，
  没有才退到配置的默认。所以 A/B **不用重启、不用改服务端状态**——评测脚本每次请求带上预算即可，
  所有臂同一个 boot（这正是判据要的东西）。`POST /settings`（`SHARED_KEYS`，`serve/server.py:7656`）也能热改，
  但它会写 `shared_path` 并影响**包括我自己在内**的所有客户端，所以不用它。
- `POST /config` 改的键是"used from the next start"（`serve/server.py:6949-6951`），**不是**热改。
- `_own_page` 只要求 `Content-Type: application/json` 且没有 foreign Origin（`serve/server.py:6904-6914`、
  `6953-6960`：没有 Origin 头就不是浏览器）——curl 能过这道门。

**判据脚本的两个坑（都是实测撞出来的，不是读出来的）**：

1. **`/opt/ai/bin` 里的老脚本与线上鉴权不同步**。`quality_eval.py` 不发 API key，而 `strata-022.json` 里
   `api_key = "111"`，于是每个任务 `HTTPError 401`、总分打成 `SCORED: 0/11`——**看起来像模型退步，其实是鉴权失败**。
   这台机器上 164 个脚本，凡是当年按"无鉴权"写的都有这个风险。改造版 `tools/server/quality_eval_budget.py` 从配置里读 key。
2. 本机 python 3.12.3 的 `sys.environ` **不存在**（`os.environ` 在）。我第一版改造用了 `sys.environ`，
   每个任务 `AttributeError`，又是一次"0/11 假象"。

| **总秒数** | 106.9 | 78.2 | **60.7** | 94.5 |
| 判分 | 11/11 | 11/11 | 11/11 | 11/11 |

### 这一轮最重要的结论不是预算，是噪声

**两次基线之间（同 boot、同配置、无预算）：每任务平均相对差 24.5%，总 token 差 28%（3,969 vs 2,866），
`zh-prose-2` 一条从 1,817 跳到 761（−58%）。** 这与调优计划 §7 那句"本机生产配置下的输出不可复现"
（同臂连跑三次 `text_sha256` 都不同）是同一件事的量化版本。

推论，且它推翻了一个写在判据脚本注释里的前提：

> `quality_eval.py` 头部说"引擎是贪心的，A/B 对照显示重启间输出逐位相同，所以**每臂一次就够**"。
> **这台机器上这句话不成立**——同一臂两次跑的 token 数差 28%。凡是拿这个脚本做的"一臂一次"结论都要重估。

因此本轮的结论按强度分开写：

- **站得住**：预算机制确实生效并被量到——在两个真正被预算咬住的任务上（自然思考 > 1024），
  `b256` 把 token 打到基线均值的 **−57% / −67%**（1,140→488、1,289→420），
  **答案长度几乎不变**（340 vs 336 字符、250 vs 245 字符），11 个判分题**答案逐字相同**、全部正确，
  思考字符从 1,582→469、2,976→524。总墙钟 60.7 s 对两次基线均值 92.6 s（**−34%**）。
- **站不住、需要更多 rep**：短任务上的 ±30% 摆动（`logic-1` +30%、`json-2` +27%、`extract-1` +30%）
  全在 24.5% 的噪声带里，**不能当作"预算让短任务变笨/变聪明"**。
- **`b1024` 在这个任务集上基本等于没改**（总 token 3,427 对基线均值 3,418，+0.3%；总秒数 94.5 对 92.6，+2%）：
  13 个任务里只有 2 个的思考长度超过 1024，其余 30–159 token 根本碰不到线。

### 判据本身要改：这个任务集不是 agent 形状

eval 里的短任务思考只花 30–159 token，而我自己的 agent 步（同一台机器、同一个模型）日志里是
**746–989 token/步**。所以"预算该设多少"这个问题**不能用这套任务回答**——它测不到 agent 场景。
下一轮（L-002b）要换成**多步工具调用任务**，每臂 ≥3 次、取中位，臂为 `无 / 512 / 256`，
判据是完成率、工具调用通过率、空答案率、墙钟中位，而不是 tok/s。

**另一个要盯的点**：`zh-prose-1` 的中文占比从 78.3% 掉到 61.5%（答案长度没变，但 ASCII 成分变多）。
这可能是"思考被截短后答案更爱夹英文"，也可能是噪声——单点读数，**未定论**，L-002b 里要带上这个指标。

**墙钟在这台机器上是被污染的**：只要第二条流在解码，单流就腰斩，所以这个实验的**主判据是 token 数与判分**，
秒数只当趋势看。

## L-004 · "不可复现"到底是采样还是引擎（探针，已跑）

`tools/server/probe_determinism.py`：同一个中文长文 prompt 各跑 3 次，两种模式——按 eval 的做法**省略**采样键，
与显式 `temperature: 0`。原始日志 `/opt/ai/runs/probe-determinism.log`。

| 模式 | 3 次的思考字符 | 答案哈希 | 秒数 |
|---|---|---|---|
| 省略采样键（服务端套配置的 0.6/0.95/20） | 4367 / 4540 / 5089 | **3 个都不同** | 55.8 / 54.4 / 36.7 |
| `temperature: 0` | 4337 / 4639 / 4489 | **3 个都不同** | 27.9 / 26.9 / 26.1 |

**结论：钉温度钉不住输出。** 6 次跑出 6 个不同哈希，两边思考长度都在摆。所以 L-002 那 24.5% 的噪声是
**引擎级**的（批处理、MTP draft 接受、缓存状态），不是采样参数。**没有"钉温度就能少跑几次"这条捷径**，
≥3 次取中位这条规矩不能省。这与调优计划 §7"同臂连跑三次 `text_sha256` 三个值、draft 数也不同"是同一件事，
这里是独立复现。

顺带两条：

- **`reasoning_effort: high` + 预算 12288 会把 `max_tokens` 吃穿**：6 次全部 `finish=length`（2200 token 用尽），
  答案被拦腰截断。生产里任何发小 `max_tokens` 的客户端都会拿到半截答案——这是配置层面的真实风险，不是实验瑕疵。
- 省略采样键那三次的秒数（55.8 / 54.4 / 36.7）比钉温度那三次（27–28 s）长一倍，**这是我自己同时在解码造成的污染**，
  不是温度的作用：跑钉温度那三次时我正好在等待、没有生成。同一件事第二次印证"本机秒数不能直接比"。

## L-005 · agent 形状的预算实验（第一轮，短上下文与长上下文）

`tools/server/agent_budget_ab.py`：客户端自己执行工具的循环（`add` / `lookup` / `slug` 三个工具），8 个任务都有
可判分的标准答案；臂 = 无预算 / 512 / 256，交错跑（rep1 三臂、rep2 三臂……），`temperature: 0` 钉住。
原始日志 `/opt/ai/runs/agent-budget-ab.log`、`…-long.log`。

**短上下文（6 个任务，无历史）**：

| 臂 | 完成率 | completion token 中位 | 畸形工具调用 | 每任务秒数中位 |
|---|---|---:|---:|---:|
| 无预算 | 6/6 | 1,017 | 0 | 5.0 |
| 512 | 6/6 | 1,055 | 0 | 4.0 |
| 256 | 6/6 | 1,004 | 0 | 3.7 |

**预算在短工具任务上等于没改**（−1.3% / +3.7%，都在噪声里）：一次工具调用的思考只有 100–200 token，
够不到 256 那条线。这**否证了"思考预算是我现在最大的免重编译杠杆"这个假设**——至少对短上下文的一步是这样。

**长上下文（同一批任务 + 300 行 / 26,099 字符的会话历史 + 2 个必须从历史里取数的事实题，8 个任务）**：

| 臂 | 完成率 | completion token 中位 | 畸形工具调用 | 每任务秒数中位 |
|---|---|---:|---:|---:|
| 无预算 | 8/8 | 2,143 | 0 | 7.1 |
| 512 | 8/8 | 1,977（−7.7%） | 0 | 3.4 |
| 256 | 8/8 | 1,921（−10.4%） | 0 | 3.0 |

秒数不能按这张表读：三次 rep 的污染程度差很多（rep1 三臂 102 / 88 / 84 s，rep3 三臂 29.6 / 29.4 / 26.0 s——
rep3 那三次我正好在睡觉）。**按 rep 内部配对读**：污染最小的 rep3 里 256 臂比无预算省 **12%**，512 臂省 **0.7%**。

**结论（这条否证了我自己上一轮的假设）**：思考预算对 agent 形状的一步只是**小杠杆（≤10%）**，不是大杠杆。
原因是工具调用那一步本来只想 100–250 token，256 的线都够得着但不吃紧；
完成率与工具调用通过率三臂全同（8/8、0 畸形）。
我自己在 100K+ 上下文里每步想 746–989 token，那是**上下文规模**造成的，不是任务形状造成的——
所以"预算该设多少"要在**几十万 token 的上下文**里测，而那要付 187K prompt token 的 prefill（102 s 一轮），很贵。

**便宜的替代做法（下一轮）**：服务端的 `POST /settings` 是**真热改**且会落到所有客户端，
所以可以直接把 `reasoning_budget_tokens` 临时改成 512，观察**我自己**接下来几步的
`thinking: N of budget 512 …` 日志行，再改回 12288。代价是那几步我自己变笨一点，
好处是零重启、零额外 prefill、测的正是真实负载。**要放在一轮的末尾做，别在关键分析中途做。**

## L-009 · `reasoning_effort`：先读机制，再交错测四臂（免重启，2026-10-24）

**机制（读代码，`serve/server.py` 0.2.2）**：`EFFORT_TEXT`（186 行）说明 effort **就是一句插进 prompt 的
自然语言**——`EFFORT_TURN = "<|im_start|>system\n{}<|im_end|>\n"`，`render_prompt()`（4556-4573）对
**非默认** effort 的请求，把会话按默认渲染、只在答案前插这一句（这样前缀不变、会话缓存还能命中）；
`enable_thinking: false` 时尾巴是空串（模板的空思考块）。`high` 不在 `EFFORT_TEXT` 里，因为它就是默认，
不插句。**引擎层没有任何 effort 上限**；真正封顶的只有 `reasoning_budget_tokens` 与"关思考"。

**顺带核实**：`/settings` 只认 `none, low, medium or high`（7550-7552），`off` 不在文档值里；
实测 `none` 与 `off` 在这台机器上等价（同一 prompt：都是 16 completion token、同一 `text_sha`
`b17bc92de6ba8a97`）。**要用就用 `none`。** 线上配置**没有** `reasoning_effort` 这个键
（只有 `reasoning_budget_tokens = 12288`），所以 `config_effort = None`：服务端不给默认，
**每个客户端自己定**——改配置默认只影响不传 effort 的客户端，对我们自己的会话无效。

**测量**（`tools/server/agent_budget_ab.py` 长上下文形态，8 个可判分任务，温度钉 0，交错 3 轮，
原始日志 `/opt/ai/runs/effort-long.log`，数据 `/opt/ai/runs/agent-budget-ab-long-effort.json`）：

| 臂 | 通过（中位） | completion token（中位） | 每任务秒（中位） |
|---|---:|---:|---:|
| `0@high`（今天的样子） | 8/8 | 1,949 | 10.8 |
| `0@off` | **7/8** | **514（−74%）** | 7.6 |
| `0@low` | 8/8 | 1,940（−0.5%） | 12.3 |
| `0@medium` | 8/8 | **1,411（−28%）** | 10.7 |

**读得出来的**：
- `low` 与 `high` 差 0.5%，**在噪声里**——那句话不起作用。`medium` 那句（"想任务需要那么多，别啰嗦"）
  在 3 轮里都把思考砍掉约 28%，且 3 轮都是 8/8。
- `off/none` 砍掉 74%，但**每一轮都丢任务**（7/8、6/8、7/8，中位 7/8）：失败模式很一致——
  **内容对但答案格式不全**（`t2lookup` 只答 `driver=595.71.05` 漏了 `slots=`；`t_slug3` 把
  `disk,space,alert` 写成了散文）。这正是"空答案率/工具调用通过率"那一类，不是随机抖动。
- **秒那一列被污染**：我这轮一边生成一边让它跑，本机并发会把单流腰斩（rep 与 rep 之间总时长
  从 53 s 摆到 111 s）。所以 `medium` 省了 28% token 却没省秒，**不能当成"省时间"的结论**；
  token 数与通过率两列不受争用影响，才是能用的证据。

**结论（诚实版）**：`medium` 是本轮唯一"免重启、砍掉可观思考 token、在这 8 个任务上没看到正确性损失"
的候选。**但这 8 个任务是查表/短链式**，不构成质量门。下一步（也不需要停机）：给工装加**真正需要推理**
的可判分任务（多步算术、约束满足、跨行计数），再对 `high` 与 `medium` 交错 ≥3 轮；只有那时才谈

## L-025 · read-ahead 到底多大工程（静态阅读，未测；2026-10-24 04:5xZ）

接着 L-024 往下读三处，把"加一条不要槽的读命令"这个说法**改小**了：

  三条流时读能边读边解码，说明那次 ensure 要么没长、要么安静得很快——**这两种情况各占多少，未测**。
- 会话状态（ids + checkpoint）是**最后一步**才复制进槽的（15432-15464，线上 42.6 ms），而且引擎本来就会
  把 checkpoint 在槽之间搬/lend（`STRATA_SLOT_CKPT_MOVE`，15436-15448）——**"先读后挂"要用的 adopt 路径已经有一半**。

  但它是**按槽记账**的（服务端 `_park_slot(slot)`，`server.py:1634`；命令是 `SAVE`/`RESTORE`，12064），
  所以它是**起点不是现成件**。
